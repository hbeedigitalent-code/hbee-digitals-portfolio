# Admin route and 2FA security audit

First written as a read-only audit (Phase 5 of A2); **updated after remediation** (A3). Each finding below states its
current status. Statements about RLS are code-level assumptions unless marked verified; the database was never queried.

## How access is enforced

| Layer | Covers | Requires |
|---|---|---|
| `middleware.ts` | Every `/admin/*` **page** | Session → active `admin_users` row → valid user-bound 2FA cookie (else redirect to `/admin-2fa-challenge`). Only `/admin/login` and `/admin/reset-password` are exempt |
| `requireActiveAdmin()` (`src/lib/admin-api-auth.ts`) | Admin **API** routes | Session → 2FA cookie → active admin row, checked **before** any read. 401 generic if the cookie is missing |
| Nothing | Any `/api/*` route that does not call a guard itself | The middleware matcher does not include `/api/*` |

Second factor: a **custom TOTP system** (speakeasy secrets in `admin_2fa` + a signed, user-bound, 12-hour cookie). The
installation does **not** use Supabase-native MFA / assurance levels (no `auth.mfa` or `aal` anywhere in the code), so the
cookie is the one verified mechanism and is what every admin page and API enforces.

## A. Fixed in this work (code; verified by tests)

| # | Was | Now |
|---|---|---|
| S1 | `POST /api/sitemap` — **unauthenticated** write of request content to `public/sitemap.xml` | **Route deleted.** The sitemap is generated by `src/app/sitemap.ts`; the SEO page's button is removed. A test fails if any API route can write to the filesystem |
| S2 | `GET /api/backup` — **unauthenticated**; read `blog_posts.*` as whoever called | `requireActiveAdmin()` first; reads through the privileged client with an **explicit column list** (no `*`, no contact or credential columns) |
| S3 | `GET /api/analytics` — **unauthenticated** counts of `contact_submissions` / `subscribers` via the anon client | `requireActiveAdmin()` first; aggregates only (no row, name, email or message); a failed read is a 500, not a silent zero |
| S4 | `GET /api/google-analytics` — returned **hard-coded fake numbers** | **Route deleted** (nothing called it) |
| D1 | `/api/export` carried its own copy of the admin gate | Uses the shared `requireActiveAdmin()`; what is exported is unchanged (still the caller-role client, still a fixed 10-table allow-list) |
| F1 | **2FA bypass with a password alone.** `POST /api/admin/2fa/disable` and `/setup` required only a signed-in admin *session*. An attacker with just a password could switch 2FA off (or replace the secret and set `is_enabled=false`), after which `/2fa/status` stamped them "verified" | `setup` on an *enabled* factor requires a completed 2FA verification; `disable` is refused outright while enrollment is mandatory (and needs a verified session under the opt-out). Exercised end to end with real TOTP codes |
| F2 | `/2fa/status` **stamped every un-enrolled admin as verified**, and **failed open**: a read error looked like "not enrolled" | Un-enrolled admins get `enrollmentRequired` and **no cookie**; the cookie is issued only by completing enrollment or a TOTP login. An unreadable `admin_2fa` record fails **closed** (500, nothing stamped). `ADMIN_2FA_ENROLLMENT=optional` is the only way to restore the old behaviour, and it is a logged opt-out, never the default |
| F3 | No rate limit on the TOTP endpoints (6-digit code) | 8 attempts / 10 minutes **per admin account** (not per IP) on `/2fa/login` and `/2fa/verify` |
| F4 | Backup codes made with `Math.random`, stored in plaintext, shown on the Profile page — and **never accepted by any login path** | Backup codes are **no longer generated, stored, returned or displayed** anywhere (enrollment page, Profile page, API). Backup-code login is deliberately **not** implemented yet |
| P1 | `/admin/reset-password` let an already-signed-in admin reach the password form with an expired link | A link is accepted only on Supabase's `PASSWORD_RECOVERY` event; the 2FA cookie is cleared when a link is accepted and after the change |
| E1 | `/admin/email-settings` pulled `smtp_password` into the browser | The page no longer reads, shows, holds or sends it (the stored value and its RLS are separate, below) |

## B. Still open — release-blocking until verified or approved

| # | Finding | Why it blocks | Needs |
|---|---|---|---|
| B1 | **RLS on every browser-queried table is UNVERIFIED** (48 tables; see `docs/admin-browser-table-access.md`). A page gate is not a control: any signed-in user can call Supabase directly | Treated as a blocker per the standing rule | Run `scripts/admin-security-preflight-readonly.sql` on staging; then move writes behind `/api/admin/…` and tighten grants (approved migration) |
| B2 | A stored `email_settings.smtp_password` may exist and its table RLS is unknown | Secret exposure | Preflight; then remove the value/column (approved migration) |
| B3 | **`admin_2fa` schema facts.** In production `secret` is `NOT NULL` and `user_id` has **no unique constraint** (per `portfolio-staging-01-bootstrap-structure.sql`). Duplicate rows make the status read fail closed (an admin is locked out until reconciled); `NOT NULL` makes the legacy `disable` write (`secret = NULL`) impossible. Not changed here | Mandatory enrollment is only safe if enrollment writes succeed | Preflight section 3; owner reconciles duplicates; the schema fix is a separate approved migration |
| B4 | **No backup-code recovery exists.** Codes written by earlier enrollments may still sit in `admin_2fa.backup_codes` in plaintext; nothing reads them | A stored secret-like value with no purpose | Remove the stored values in an approved migration (the read-only preflight does not select them). Implementing hashed, single-use backup-code login is a separate decision |
| B5 | Lost authenticator recovery is **owner-assisted**: an owner resets the `admin_2fa` row in the database (service role), after which the admin re-enrolls. There is deliberately no self-service bypass | Operational, not a code defect | Document and authorise the procedure; every reset should be recorded |
| B6 | An admin with **no 2FA record** can enroll with only a session (first-time enrollment is how the cookie is first earned). Until enrolled, that account is exactly as strong as its password | Inherent to first enrollment | Enroll every admin during a controlled window, immediately after deploying, before announcing |
| B7 | **Rate limiting fails open** if Upstash is unconfigured or unreachable (`checkRateLimit` returns `degraded`) | The TOTP limit then does not apply | Confirm `UPSTASH_REDIS_REST_URL/TOKEN` on staging and production |
| B8 | Existing 2FA cookies live up to 12 hours. An admin stamped under the old behaviour keeps access until it expires, then must enroll | Short, bounded window | Accept, or rotate `ADMIN_2FA_COOKIE_SECRET` to force it at deploy time |
| B9 | **Duplicated inline copies of the admin gate** remain in 11 admin routes (file / signed-URL routes, proposals, `growth-reviews/[id]/complete`). Each was verified to check session, 2FA cookie and admin row; a test enforces that every privileged route has all three | Drift risk, not a current hole | Consolidate onto `requireActiveAdmin()` one area at a time |
| B10 | `/api/admin/logout` is unauthenticated by design (it only clears the caller's own 2FA cookie) | None; recorded so it is not mistaken for a gap | — |

## D. Properly protected (verified in code, unchanged)

`/api/export` (allow-listed tables), `/api/send-newsletter`, `/api/admin/email-logs`, the notification routes (2FA cookie
+ admin row), `/api/uploads/*` (`authorizeUploadTarget`), `/api/cron/*` (secret), and every other `/api/admin/*` route.
`scripts/test-admin-api-authz.cjs` runs the **real** gate through ten denial scenarios against `backup`, `analytics` and
`export` and classifies all 83 routes; `scripts/test-admin-2fa.cjs` drives the real 2FA routes.

## E. Recommended order

1. Run the read-only preflight on **staging**; resolve any `BLOCKER` (B1–B3).
2. Confirm Upstash (B7) and decide the owner reset procedure (B5).
3. Deploy to **staging** with `ADMIN_2FA_ENROLLMENT` unset; enroll every admin; run the recovery matrix.
4. Only then consider production.
