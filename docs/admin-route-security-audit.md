# High-risk admin route audit (Phase 5)

Read-only audit of the code. **No route was changed, no destructive operation was run, no database was queried.**
Where a finding depends on database policies (RLS) the repository cannot show, it is marked `RLS-dependent`.

## How access is enforced today

| Layer | What it covers | Requires |
|---|---|---|
| `middleware.ts` | Every `/admin/*` **page** | Supabase session → active `admin_users` row → valid user-bound 2FA cookie (else redirect to `/admin-2fa-challenge`). `/admin/login` and `/admin/reset-password` are the only exemptions. |
| `requireActiveAdmin()` (`src/lib/admin-api-auth.ts`) | Admin **API** routes that adopt it | Session → 2FA cookie → active admin row. 401 with a generic message if the 2FA cookie is missing |
| **Nothing** | Any `/api/*` route that does not call a guard itself | The middleware matcher is `/admin/:path*`, `/admin-2fa-challenge`, `/client-portal/:path*`. **`/api/*` is not covered** |

An admin who has **not** enabled 2FA is stamped a cookie automatically by `/api/admin/2fa/status`, so "without completed
2FA" means "2FA enabled but not yet verified" for the purposes below.

## A. Properly protected (verified in code)

| Route | Guard | Notes |
|---|---|---|
| `POST /api/export` | Local gate: session → **2FA cookie** → active admin, **before** the body is parsed | Table must be in a fixed 10-table allow-list; no caller-supplied table, column or filter. Exports include `subscribers` and `messages` (PII) — admin only |
| `POST /api/send-newsletter` | `requireActiveAdmin()` first | Sends real email; the existing campaign flow |
| `GET /api/admin/email-logs` | `requireActiveAdmin()` | Replaced a direct browser read |
| `/api/notifications`, `/[id]/read`, `/read-all`, `/unread-count` | 2FA cookie **and** `admin_users` check | Session-based; fails closed |
| `/api/uploads/initiate|finalize|cancel` | `authorizeUploadTarget()` (admin + 2FA for admin contexts, client account for portal contexts) | Re-checked at finalize |
| `/api/cron/*` | Cron secret | Not session-based by design |
| All `/api/admin/*` Growth, merchant, client, proposal, project routes | `requireActiveAdmin()` | Unchanged by this work |
| `POST /api/admin/logout` | None (by design) | Only clears the 2FA cookie |

For a user **without a completed 2FA verification**: every admin page redirects to the challenge, and every route in the
table above answers 401. That was not weakened by A1/A2.

## B. SECURITY ISSUES (not just unfinished)

| # | Route | Finding | Severity | Evidence |
|---|---|---|---|---|
| S1 | `POST /api/sitemap` | **No authentication.** Writes the request body to `public/sitemap.xml` (`writeFile`). Anyone who can reach the URL can attempt to overwrite the public sitemap with arbitrary content (SEO poisoning, link injection). On Vercel the function filesystem is read-only, so the write should fail there (`EROFS`) — **not verified**; on any writable host it works. The only caller is the legacy `/admin/seo` page. The sitemap is now generated by `src/app/sitemap.ts`, so this route is dead weight | **High** (potential), Low if the host is read-only | `src/app/api/sitemap/route.ts` has no guard |
| S2 | `GET /api/backup` | **No authentication.** Despite the name it returns `blog_posts.*` using the cookie-session client, i.e. **as whoever calls it** (anonymous callers get the `anon` role). Exposure is whatever `blog_posts` RLS allows `anon` to read — if drafts are readable that is a leak. `RLS-dependent` | Medium (potential) | `src/app/api/backup/route.ts` |
| S3 | `GET /api/analytics` | **No authentication.** Returns counts and 30-day series for `contact_submissions` and `subscribers` using the server `anon` client. If either table is anon-readable (the already-known contact-submission RLS concern) these aggregates are public; if blocked they return zeros. `RLS-dependent` | Medium (potential) | `src/app/api/analytics/route.ts` |
| S4 | `GET /api/google-analytics` | **No authentication** and returns **hard-coded fake numbers** (`1247` page views…) when GA env vars exist. No data leak, but it fabricates analytics if anything ever consumes it | Low (integrity) | `src/app/api/google-analytics/route.ts` |
| S5 | `/admin/email-settings` | Reads/writes `email_settings` **directly from the browser**, including a `smtp_password` field, and **nothing in the code reads that table** (transactional email uses env vars + Resend). Credentials in a browser-readable table are only as safe as its RLS. `RLS-dependent` | Medium (potential) | `src/app/admin/email-settings/page.tsx` |
| S6 | `/admin/email-templates*`, `/admin/bulk-delete` (reads), `/admin/messages`, `/admin/seo`, `/admin/cta`, `/admin/images` | Direct browser table access (select / insert / update / delete) with no server route, so safety rests entirely on each table's RLS. These pages are behind the middleware (session + admin + 2FA), but a signed-in user of any kind can call the same Supabase endpoints from a console, so the page gate is not the control. `RLS-dependent` | Medium (potential), tied to the open RLS verification in `docs/audits/2026-09-13-database-security-audit.md` | multiple pages |

### Proposed fixes (not applied — needs approval)

| Issue | Smallest safe fix | Notes |
|---|---|---|
| S1 | **Delete** `src/app/api/sitemap/route.ts` and the "regenerate sitemap" button in `/admin/seo` (the sitemap is generated by `sitemap.ts`). Alternative: gate with `requireActiveAdmin()` and stop writing to disk | Deleting removes the capability entirely |
| S2 | Delete the route (the page that calls it uses methods the route does not implement), or gate with `requireActiveAdmin()` and use the service client deliberately | Real backups belong in Supabase, not here |
| S3 | Gate with `requireActiveAdmin()` and read through the privileged client, or delete (the Analytics page does not call it) | |
| S4 | Delete, or return `success:false` until a real GA integration exists | |
| S5 | Verify `email_settings` RLS on staging; if the table is unused drop the page, and never store SMTP credentials in a table | A database change would need its own forward/rollback plan |
| S6 | Move each page to an `/api/admin/...` route behind `requireActiveAdmin()` as was done for the other admin areas, **or** confirm RLS denies `authenticated` writes on these tables | Ties into the pending RLS verification |

## D. What "email operations" cover

- Outbound sending is done by the outbox/`deliverQueuedEvent` flow and `/api/send-newsletter` (both gated server-side).
- `/admin/email-logs` (gated API) is the real log viewer and is the only email page worth promoting to the navigation.
- `/admin/email-templates` and `/admin/email-settings` edit tables nothing else reads; the email design system lives in code.

## E. Recommended order

1. **S1** (delete or gate `/api/sitemap`) — smallest change, highest potential impact.
2. **S2–S4** — delete or gate the three unauthenticated read routes.
3. Run the RLS verification already specified in the database audit, then decide **S5/S6**.
4. Only then decide whether any of the unlisted pages enter the navigation (`email-logs`, `notifications`, `export`).
